# Информационно-аналитический сервис

Карта термоточек и контуров гари + REST API + выгрузка векторов и аналитической
справки. Соответствует разделу 4 критериев (12 баллов).

## Запуск

```bash
pip install -r ../requirements.txt
python -m service
```

* карта — <http://127.0.0.1:8000>
* документация REST API (Swagger) — <http://127.0.0.1:8000/docs>

Ничего настраивать не нужно: каталог данных и веса ищутся автоматически.
Переопределить можно флагами или переменными окружения:

| флаг | переменная | по умолчанию |
|---|---|---|
| `--data-dir` | `FIRE_DATA_DIR` | автопоиск `fire-train-renamed.tar` рядом с проектом |
| `--weights-dir` | `FIRE_WEIGHTS_DIR` | `solution/weights` |
| `--source model\|truth` | `FIRE_SOURCE` | `model` |
| `--port` | `FIRE_PORT` | `8000` |
| `--host` | `FIRE_HOST` | `127.0.0.1` |

```bash
python -m service --data-dir /data/fire --weights-dir /data/weights --port 8080
```

## Что показывает

Сервис работает на **обучающем** наборе: только там есть геопривязка (`epsg`,
`x_min/y_min/x_max/y_max`) и даты (`acq_datetime` у AF, `date_pre`/`date_post`
у BS). У тестовых чипов в `meta.csv` нет ни координат, ни дат — их нельзя
положить на карту, и восстанавливать их запрещено критериями.

По умолчанию карта строится по **предсказаниям нашей модели** — тех же весов,
что дают `submission.csv`. Карта из эталонных масок ничего бы не
демонстрировала. Эталон доступен через `--source truth`, и в таком режиме
сервис явно помечает это и в интерфейсе, и в каждом ответе API; это удобно,
чтобы сравнить предсказание с разметкой на одном экране.

## REST API

Всё, что есть в интерфейсе, доступно без него. Основной запрос:

```bash
curl "http://127.0.0.1:8000/api/query?bbox=44.88,48.53,45.03,48.63&date_from=2019-04-01&date_to=2019-05-31"
```

```bash
curl -X POST http://127.0.0.1:8000/api/query \
     -H "Content-Type: application/json" \
     -d '{"bbox":[44.88,48.53,45.03,48.63],"date_from":"2019-04-01","date_to":"2019-05-31"}'
```

Вместо `bbox` можно прислать произвольный полигон:

```bash
curl -X POST http://127.0.0.1:8000/api/query \
     -H "Content-Type: application/json" \
     -d '{"geometry":{"type":"Polygon","coordinates":[[[44.88,48.53],[45.03,48.53],[45.03,48.63],[44.88,48.63],[44.88,48.53]]]},
          "date_from":"2019-04-01","date_to":"2019-05-31"}'
```

| эндпоинт | назначение |
|---|---|
| `GET /api/health` | состояние, источник контуров, устройство, размер кэша |
| `GET /api/catalog` | покрытие данными: bbox, диапазон дат, число чипов |
| `GET /api/chips?kind=bs` | футпринты чипов (слой «покрытие данными») |
| `GET\|POST /api/query` | термоточки + контуры + справка |
| `GET /api/export/contours.geojson` | контуры гари, GeoJSON |
| `GET /api/export/hotspots.geojson` | термоточки, GeoJSON |
| `GET /api/export/report.json` | справка, JSON |
| `GET /api/export/report.csv` | справка, CSV (UTF-8 с BOM, разделитель `;`) |

## Векторная выгрузка

GeoJSON в **EPSG:4326** (`urn:ogc:def:crs:OGC:1.3:CRS84`), как требует RFC 7946.
Атрибуты каждого контура:

| поле | что это |
|---|---|
| `contour_id` | идентификатор контура |
| `chip_id` | исходный чип |
| `severity_class` | 1 / 2 / 3 |
| `severity_label` | слабое / умеренное / сильное |
| `area_ha` | площадь, гектары |
| `pixels` | число пикселей (по нему считается площадь) |
| `gsd_m` | разрешение, м |
| `source_epsg` | исходная проекция чипа |
| `date_pre`, `date_post` | даты снимков «до» и «после» |
| `fire_event_id` | идентификатор пожара |

## Как считается площадь

```
площадь = число пикселей × gsd² / 10000   (га)
```

Пиксели считаются в **исходной проекции чипа** — это UTM (EPSG:326xx), она
метрическая, и площадь в ней определена корректно. На карту и в GeoJSON
геометрия уходит уже перепроецированной в WGS 84; площадь по перепроецированному
полигону не пересчитывается, потому что планарная площадь в географических
координатах физического смысла не имеет.

Формула сверена с колонкой `burn_area_ha` из `meta.csv` организаторов: для
`BS_tr_000001` маска содержит 11360 + 10 + 0 = 11370 горелых пикселей при
gsd = 20 м, что даёт 11370 × 400 / 10000 = 454.8 га — ровно то, что стоит в
`meta.csv`. Проверено по чипам, расхождение 0.0000 га.

## Кэш и скорость

Первый запрос по новой территории прогоняет модель по чипам — на CPU это
единицы секунд на чип. Результат векторизуется и кладётся в `service/cache/`,
дальше запросы отвечают из файлов (замер: 21.9 с → 0.12 с).

Перед демонстрацией кэш имеет смысл прогреть целиком:

```bash
python -m service.precompute            # все чипы
python -m service.precompute --kind bs  # только контуры гари
```

Кэш в git не попадает (`.gitignore`) — он полностью воспроизводится этой
командой.

## Из чего собрано

| файл | ответственность |
|---|---|
| `config.py` | настройки из переменных окружения, пути относительно репозитория |
| `catalog.py` | пространственно-временной индекс чипов из `meta.csv` |
| `predictor.py` | прогон моделей по чипу + дисковый кэш |
| `geo.py` | векторизация масок, площади, перепроецирование |
| `query.py` | единственное место, где запрос превращается в ответ |
| `api.py` | FastAPI: REST + раздача интерфейса |
| `precompute.py` | CLI прогрева кэша |
| `static/` | интерфейс (Leaflet лежит локально, не с CDN) |

Интерфейс и API идут через один и тот же `query.run_query`, поэтому цифры на
карте и в ответе `curl` не могут разойтись.

Leaflet положен в `static/vendor/` намеренно: если у проверяющих не будет
интернета, подложка OSM не загрузится, но карта, векторные слои и вся аналитика
продолжат работать.
